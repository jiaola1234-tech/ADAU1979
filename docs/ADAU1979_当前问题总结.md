# ADAU1979 当前问题总结

更新时间：2026-09-27

## 1. 已确认正常

- FPGA 时钟：`100 MHz`
- I²C 速率：`100 kHz`
- U1 的 7 位地址：`0x11`
- 当前 XCI 为单芯片诊断模式：`U1=0x11`、`U2=0x11`
- `ACK_BITS=7`

`ACK_BITS=7` 表示三个写阶段都收到 ACK：

```text
设备地址 ACK：成功
寄存器地址 ACK：成功
数据 ACK：成功
```

因此，目前没有证据表明是 ACK 持续时间过短或写地址失败。

ILA 中看到 SDA 在一个 `100 MHz` 周期内由高变低，是主机释放 SDA 后从机准备 ACK 的交接过程。这个 10 ns 的瞬态不是完整的 ACK 时间，不需要修改。

## 2. 当前真正的错误

最新串口结果为：

```text
STATUS=0x00000F08
step=15 busy=0 done=0 error=1
ERROR_COUNT=0
VERIFY_EXPECT=0x00
VERIFY_ACTUAL=0xFF
```

这说明：

```text
写入阶段成功
ACK 错误计数为 0
读回阶段得到 0xFF
程序期望得到 0x00
因此初始化失败
```

失败位置为：

```text
设备：0x11
寄存器：0x00
期望：0x00
实际：0xFF
```

## 3. 当前主要可能原因

### 原因 A：寄存器 0x00 不适合立即进行严格相等校验

寄存器 `0x00` 是 `M_POWER` 控制寄存器。写入后其读回值可能受到内部电源状态或控制逻辑影响，不一定严格等于刚写入的值。

因此，当前代码中“写入 `0x00` 后立即要求读回必须是 `0x00`”的规则可能过于严格。

### 原因 B：读回控制器时序仍有问题

还需要排除以下读事务问题：

- 重复 START 时序；
- 读地址字节发送；
- 读地址 ACK 判断；
- SDA 释放和从机数据驱动的交接；
- 8 位读数据采样位置；
- 最后一字节后的主机 NACK 和 STOP。

目前仅凭 `VERIFY_ACTUAL=0xFF`，还不能区分原因 A 和原因 B。

## 4. 当前 ILA 能看到什么

当前 `probe3` 主要暴露写控制器信息：

```text
probe3[11]    ACK采样脉冲
probe3[10]    ACK采样结果
probe3[17:15]写字节编号
probe3[22:18]写控制器状态
probe3[51]   SDA输入
probe3[50]   SCL释放控制
probe3[49]   SDA释放控制
```

当前 ILA 没有直接暴露以下读回信号：

```text
verify_read_addr_ack
verify_read_data_valid
verify_read_data
verify_ack_error
```

所以现有 ILA 可以验证写 ACK，但不能完整定位读回 `0xFF` 的具体阶段。

## 5. SCL/SDA 信号极性

原来的调试定义是：

```verilog
assign i2c_scl_dbg = ~adau_scl_oe_n;
assign i2c_sda_dbg = adau_sda_i;
```

其中 `probe0` 的 SCL 显示与实际总线逻辑电平相反，SDA 没有反向。

源码中已经修正为：

```verilog
assign i2c_scl_dbg = adau_scl_oe_n;
assign i2c_sda_dbg = adau_sda_i;
```

重新生成 bit/ltx 后，ILA 应按下面理解：

```text
probe0 = 1：SCL高
probe0 = 0：SCL低
probe1 = 1：SDA高
probe1 = 0：SDA低
```

注意：已经下载到 FPGA 的旧 bit/ltx 不会自动采用这个修正，必须重新打包 IP、生成输出产品、综合、实现并下载新的 bit/ltx。

## 6. 当前结论

当前故障不是“写 ACK 太短”，而是：

```text
写 ACK 已成功，但读回寄存器 0x00 得到 0xFF，导致初始化失败。
```

## 7. 下一步建议

1. 重新生成包含 SCL 极性修正的 bit/ltx；
2. 检查读回事务，而不是继续延长 ACK；
3. 判断寄存器 `0x00` 是否应跳过严格的立即读回比较；
4. 必要时暂时只检查 `0x00` 的写 ACK；
5. 再测试寄存器 `0x01` 等可读寄存器；
6. 若仍读回 `0xFF`，需要增加读控制器专用 ILA 调试字段。
